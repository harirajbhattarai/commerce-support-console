## What Is a Seed File?

A seed file is a versioned SQL file that inserts or upserts **known, static reference data** into the database. Seed files populate tables that the application needs to function, such as the `stores` table and support knowledge articles.

Seed files are different from migrations:
- **Migrations** change structure (tables, columns, indexes)
- **Seeds** insert or update rows

Both are versioned, reviewed, and applied manually to each environment in sequence.

---

## Critical Rule: Seeds Must Never Contain Customer Data

> [!CAUTION]
> **Seed files applied to production must never contain:**
> - Customer chat messages or conversation history
> - Session IDs from staging test sessions
> - Customer email addresses, names, or order numbers from test runs
> - Any data that was generated by staging test activity
>
> Every seed file must have `Contains Customer Data: NO` in its header.
> If a seed file would need to say `YES`, it must not be applied to production — ever.

---

## File Naming Convention

```
SSSS_short_description_of_seed.sql
```

- `SSSS` is a zero-padded 4-digit sequential number starting from `0001`
- Use underscores, lowercase, no spaces
- Example: `0003_knowledge_pack_6_5_hoverboard_bundle_v2.sql`

**Always use the next available number.**

---

## Required Header Block

Every seed file must start with this header:

```sql
-- =============================================================================
-- SEED: SSSS_description.sql
-- =============================================================================
-- Purpose:
--   [What reference data this inserts and why it is needed in production]
--
-- Target Tables:
--   - table_name (INSERT ... ON CONFLICT DO UPDATE / DO NOTHING)
--
-- Safe for Production: YES
-- Contains Customer Data: NO
-- Idempotent: YES
--
-- Derived From:
--   - [Document or approval source — e.g. PRODUCT_SUPPORT_PASSPORT_6_5_HOVERBOARD_BUNDLE_V1.md]
--   - Confirmed by: [store owner name, date]
--
-- Staging Test:
--   [ ] Applied to staging Supabase on: YYYY-MM-DD
--   [ ] All relevant /api/test-agent queries return correct matched answers
--   [ ] No unexpected fallback replies for covered topics
--
-- Author: [name]
-- Date: YYYY-MM-DD
-- =============================================================================
```

## Idempotency Requirement (Strict)

All seed SQL **must** use `ON CONFLICT` to prevent duplicate inserts if the file is run more than once.

### For `stores` Table (Primary Key Conflict)

```sql
INSERT INTO stores (id, name, domain)
VALUES ('hoverboard_store', 'Hoverboard Store UK', 'hoverboardstore.co.uk')
ON CONFLICT (id) DO UPDATE
SET name = EXCLUDED.name, domain = EXCLUDED.domain;
```

### For `support_articles` and `product_knowledge` (Title + Store Conflict)

These tables use UUID primary keys, not natural keys. To make inserts idempotent, use a `UNIQUE` constraint or a lookup pattern. 

**Recommended pattern — delete and re-insert by known title:**

```sql
-- Idempotent: remove any existing row with the same store_id + title, then re-insert
DELETE FROM support_articles
WHERE store_id = 'hoverboard_store'
  AND title = 'Exact Unique Article Title Here';

INSERT INTO support_articles (store_id, title, content, intent_tags, channel)
VALUES (
  'hoverboard_store',
  'Exact Unique Article Title Here',
  'Full article content here.',
  ARRAY['intent_1', 'intent_2'],
  'shopify'
);
```

> [!NOTE]
> The delete-then-insert pattern is safe here because the title is a known, controlled business value — not customer-generated content. It allows the seed to be re-run with updated content without duplicating rows.

**Alternative for tables with a UNIQUE constraint on (store_id, title):**

```sql
INSERT INTO support_articles (store_id, title, content, intent_tags, channel)
VALUES (
  'hoverboard_store',
  'Exact Unique Article Title Here',
  'Full article content here.',
  ARRAY['intent_1', 'intent_2'],
  'shopify'
)
ON CONFLICT (store_id, title) DO UPDATE
SET content = EXCLUDED.content,
    intent_tags = EXCLUDED.intent_tags,
    channel = EXCLUDED.channel;
```

> Check whether a UNIQUE constraint on (store_id, title) exists before using this pattern. If not, use delete-then-insert.

## What Tables Are Safe to Seed?

| Table | Safe to Seed | Notes |
|:---|:---|:---|
| `stores` | ✅ Yes | Business reference data. Use `ON CONFLICT (id) DO UPDATE`. |
| `support_articles` | ✅ Yes | Knowledge base articles from approved Product Support Passports. Use delete-then-insert by title. |
| `product_knowledge` | ✅ Yes | Product-specific knowledge chunks from approved passports. Use delete-then-insert by title. |
| `chat_logs` | ❌ Never | Contains customer messages. Never seed production with staging chat data. |
| `conversations` | ❌ Never | Contains customer session data. |
| `messages` | ❌ Never | Contains customer message content. |
| `agent_replies` | ❌ Never | Contains staff message drafts from staging tests. |
| `reply_drafts` | ❌ Never | Contains draft replies from staging tests. |
| `escalations` | ❌ Never | Contains staging test escalation records. |
| `staff_notes` | ❌ Never | Contains staff notes from staging tests. |
| `article_chunks` | ⚠️ Only after Phase 3A | Vector embedding chunks — only after clean knowledge is seeded. |

## Knowledge Seed Approval Process

Before any `support_articles` or `product_knowledge` seed file is written, the following must be true:

1. The **Product Support Passport** for the product family is complete and approved (Status: ✅ Approved)
2. The passport has been **reviewed and signed off by the store owner**
3. All `[CONFIRM]` items in the passport are resolved — no placeholders remain
4. The knowledge chunk schema in `backend/docs/KNOWLEDGE_CHUNK_SCHEMA_PLAN.md` has been followed
5. Each chunk in the seed has a unique, descriptive title
6. All safety-related chunks (battery/fire/smoke) have `risk_level = 'high'`

> [!WARNING]
> Do not write a knowledge seed from a draft passport. A draft passport with `[CONFIRM]` placeholders produces inaccurate knowledge chunks that will give wrong answers to customers in production.

## How to Apply a Seed File

### To Staging

1. Confirm the relevant migration (table creation) has already been applied to staging
2. Open Supabase Staging Dashboard → SQL Editor
3. Paste the full contents of the seed file
4. Click **Run**
5. Confirm no errors
6. Test using `/api/test-agent` with at least 5 queries covered by the new seed:
   ```
   GET /api/test-agent?q=<customer_question_covered_by_new_seed>
   ```
7. Confirm the `matched_source` in the response matches the new article title
8. Update the seed file header with staging test date and result

### To Production

1. Staging tests must be complete first
2. Confirm the production backup is taken (Step 4 of release checklist)
3. Confirm the required migrations have already been applied to production
4. Open Supabase Production Dashboard → SQL Editor
5. Paste the full contents of the seed file
6. Click **Run**
7. Confirm no errors
8. Update the Applied Seed Registry below and in `DATABASE_PROMOTION_WORKFLOW.md`
